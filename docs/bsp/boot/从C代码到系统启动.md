# 从 C 代码到系统启动：读懂汇编、地址与运行环境

阅读启动源码时，常见的困难是：C 函数本身能看懂，但不知道 CPU 怎样进入这个
函数、参数从哪里来，以及为什么进入前还要设置栈、清零内存、搬运代码。这些问题
贯穿 BootROM、GSL、U-Boot、Linux 和应用启动的全过程。

在 Linux 应用中，装载程序、建立地址空间和准备初始栈的工作已经有人完成。沿启动
链向前阅读，就会逐步看到这些条件由谁建立。下面从熟悉的 C 函数调用出发，把
寄存器、内存、汇编、链接布局和程序装载连起来，最后回到内核和应用入口。

指令以 Cortex-A7 使用的 32 位 Arm 为例。实际片段来自当前工作区的 GSL、
U-Boot 2022.07 和 Linux 5.10 源码；手写示例会单独说明。GSL 是这套平台中准备
DDR、装载后续引导程序的阶段，U-Boot 接着准备并启动 Linux。

## 1. 一次 C 函数调用怎样变成 CPU 动作

### 1.1 从 `board_init_f(0)` 看参数和入口

在 C 中调用早期初始化函数，可以写成：

```c
board_init_f(0);
```

U-Boot 的 `crt0.S` 中，对应的是：

```asm
mov r0, #0
bl  board_init_f
```

`r0` 是 CPU 内部的寄存器，能存放一个 32 位值。这里约定把第一个整数参数放在
`r0` 中。`mov r0, #0` 因而完成了实参准备：将数值零写入 `r0`。`#` 标出立即数，
表示指令中给出的数值。

随后，`bl board_init_f` 转到函数入口，同时在 `lr` 寄存器中记录返回位置。
函数结束时，返回代码利用保存的位置接着执行调用点后面的指令。CPU 执行的是
这些明确的数据传递和跳转动作。

读当前启动代码，先认识下面几个寄存器：

| 寄存器 | 在这些示例中的用途 |
| --- | --- |
| `r0`～`r3` | 传递前几个整数或指针参数，也用作临时寄存器 |
| `r0` | 还用于返回一个 32 位整数或指针 |
| `sp`，即 `r13` | 保存栈当前使用边界的地址 |
| `lr`，即 `r14` | 普通函数调用中保存返回位置 |
| `pc`，即 `r15` | 程序计数器，关联指令执行位置 |

C 编译器和汇编代码采用相同的参数、返回值和寄存器保存约定，就能互相调用。
这些约定属于应用二进制接口（ABI），当前整数调用示例遵循
[Arm AAPCS32](https://github.com/ARM-software/abi-aa/blob/main/aapcs32/aapcs32.rst)。

### 1.2 把调用和返回完整走一遍

下面用手写汇编说明这个 C 函数的行为：

```c
unsigned add_one(unsigned value)
{
    return value + 1;
}
```

一种对应实现是：

```asm
add_one:
    add r0, r0, #1
    bx  lr
```

假设调用处已经具备运行条件，执行以下片段：

```asm
    mov r0, #41
    bl  add_one
after_call:
    mov r1, r0
```

执行到 `bl` 时，`r0` 中的 41 是实参，`lr` 保存回到 `after_call` 所需的地址。
进入 `add_one` 后，`add r0, r0, #1` 将 `r0` 加一，因此返回值已经放在 `r0` 中。
`bx lr` 按 `lr` 中的目标跳转，回到调用处；最后的 `mov r1, r0` 取得结果 42。

```text
调用处：r0 = 41
        │ bl：保存返回位置，转到 add_one
        ▼
add_one：r0 = r0 + 1
        │ bx lr：按保存的位置返回
        ▼
调用处：取得 r0 中的 42
```

这也解释了三个容易混淆的写法：`b 标签` 直接跳转；`bl 标签` 保存返回位置后
跳转；`bx 寄存器` 使用寄存器里的目标跳转。`bx lr` 常用于返回，具体去哪里仍由
`lr` 当时保存的值决定。第 6 节会看到启动代码主动修改这个值的情况。

### 1.3 函数里再调用函数，原来的返回位置放在哪里

如果 A 调用 B，`lr` 先记录返回 A 的位置；B 再调用 C 时，新的 `bl` 会改写
`lr`。B 必须保存自己回到 A 所需的信息，才能在 C 执行结束后继续正确返回。

编译器通常使用栈保存这类调用状态，也会把部分局部对象和需要保留的寄存器放到
栈上。寄存器位于 CPU 内部，栈则占用 RAM；`sp` 把二者联系起来，告诉当前代码
栈使用到了哪个位置。至于启动时谁准备这块 RAM 和 `sp`，第 3 节继续解释。

## 2. 指令怎样访问内存和执行循环

### 2.1 一个地址与这个地址里的数据

在 C 中，指针值 `p` 和解引用 `*p` 是不同的操作。下面三条汇编体现同样的区别。
示例假设 `0x1000` 对应一块已准备好的可写 RAM，用它演示地址关系：

```asm
ldr r0, =0x1000
ldr r1, [r0]
str r2, [r0]
```

第一条得到数值 `0x1000`，并把它放进 `r0`。第二条把 `r0` 当作地址，从该地址
读取一个 32 位值到 `r1`。第三条反过来，把 `r2` 中的 32 位值写入该地址。
其数据关系可以用 C 表达：

```c
uint32_t *p = (uint32_t *)0x1000;
uint32_t value = *p;
*p = another_value;
```

`ldr r0, =表达式` 是汇编器支持的伪指令。汇编器会根据表达式选择适当指令，
例如直接形成常量，或从程序附近保存的常量中读出它。最终效果是让 `r0` 得到
表达式的值。`ldr r1, [r0]` 中的方括号则明确表示通过地址读取内存。
[GNU as 对这类伪指令的说明](https://sourceware.org/binutils/docs/as/ARM-Opcodes.html)
也列出了后面会用到的 `adr`。

带偏移的访问同样可以联系 C 指针理解：

```asm
ldr r0, [r9, #16]
```

它从 `r9 + 16` 指向的位置读取一个 32 位值。若 `r9` 是结构体指针，16 恰好是
某字段的字节偏移，这条指令就读取了那个字段。后面 U-Boot 的
`[r9, #GD_RELOC_OFF]` 使用的就是这个机制。

### 2.2 比较和循环怎样执行

GSL 的 `clear_data` 用循环清零内存。下面保留实际循环指令；进入循环时，
`r0` 指向当前写入位置，`r1` 为零，`r2` 为结束地址，`r3` 为 4：

```asm
clear_data_loop:
    str  r1, [r0]
    adds r0, r0, r3
    cmp  r0, r2
    blt  clear_data_loop
    bx   lr
```

一次循环写入 4 字节零，再把写入位置增加 4。`cmp r0, r2` 比较当前位置和
结束地址，把结果记在处理器的条件标志中。随后 `blt` 检查“小于”的条件，
满足时跳回循环开头，否则继续向下执行返回指令。

这里的 `blt` 是 `b` 加条件 `lt`，表示按有符号比较结果判断是否跳转。它与
保存返回位置的 `bl` 是两种不同指令。理解这种条件后缀后，读 `beq` 和 `bne`
也有了依据：它们分别在相等和不相等时跳转。

`adds`、`subs` 末尾的 `s` 表示运算还会更新条件标志。是否利用这些标志，要看
后面有没有相应的条件指令。上述循环实际依据的是紧邻 `blt` 的 `cmp` 结果。

## 3. 运行 C 代码以前需要准备什么

### 3.1 代码、初值和运行中的数据各有位置

设想有两个静态存储期变量：

```c
unsigned retry_limit = 3;
unsigned retry_count;
```

C 语义要求它们在相应初始化完成后分别具有 3 和 0。CPU 上电不会根据这两行
源码自动给 RAM 赋值，这些内容要通过程序装载和启动代码建立。

编译和链接时，常见的内容组织如下；优化和链接规则会影响具体对象的安排：

| 区域 | 通常保存什么 | 启动时要满足的条件 |
| --- | --- | --- |
| `.text` | 函数的机器指令 | 指令已位于可执行的位置 |
| `.rodata` | 只读常量 | 代码能按预期地址读取 |
| `.data` | 带非零初值的可写数据，如上面的 `retry_limit` | 初值已放到运行时使用的位置 |
| `.bss` | 需要零初值的静态存储期数据，如 `retry_count` | 对应运行内存已经清零 |
| 栈 | 函数调用状态和部分局部对象 | 有可用 RAM，且 `sp` 已指向正确位置 |

`.bss` 主要在输出文件中记录所需空间，装载或启动时再建立零值，可以避免为一大
块零数据保存同样大小的文件内容。`.data` 的初值若最初位于另一处，则需要复制；
如果前一阶段已把它装载到正确位置，后续就可以使用已准备好的内容。

这类准备通常称为建立 C 运行环境。每一阶段会按自己要执行的代码准备必要条件；
U-Boot 的早期 C 代码还约定使用专门的数据区，第 7 节会解释这个阶段性安排。

### 3.2 设置栈指针实际改变了什么

GSL 的入口中有以下指令：

```asm
ldr r0, =STACK_ADDR
mov sp, r0
```

第一条得到选定的栈地址，第二条将它写入 `sp`。之后，函数使用栈时才有了正确的
地址依据。写入 `sp` 只改变寄存器中的值，地址所指的 RAM 必须已经能读写。

GSL 早期使用芯片内部 SRAM，随后配置 DDR 控制器并进行训练，让外部内存可以
可靠访问。U-Boot 在这条启动链中获得控制权时，DDR 已经可用，可以把自己的栈
安排在 DDR 中。

U-Boot 的栈设置还会看到：

```asm
bic r0, r0, #7
mov sp, r0
```

`bic` 将数值中对应的位清零。这里相当于 `r0 &= ~7u`，清掉最低三位，使地址
满足 8 字节对齐。这样，调用代码和被调用代码就能按共同的栈对齐约定工作。

### 3.3 把 GSL 清零 `.bss` 的参数读出来

再看 GSL 调用 `clear_data` 前的实际片段：

```asm
ldr  r0, =__bss_start
mov  r1, #0
ldr  r2, =__bss_end
subs r2, r2, r0
bl   clear_data
```

`__bss_start` 和 `__bss_end` 是链接时定义的边界符号，它们的值分别是这块区域
的起始地址和结束地址。第三条取得结束地址，第四条执行减法，使 `r2` 变成字节数。
因此在调用前，三个寄存器分别表达：

| 寄存器 | 当前值的含义 |
| --- | --- |
| `r0` | 从哪里开始写 |
| `r1` | 写入零 |
| `r2` | 要清零多少字节 |

`clear_data` 内部再把长度加到起点上，得到第 2.2 节循环使用的结束地址。
这样读完整个过程，就能连接“链接器定义边界”“汇编准备参数”“循环写零”这三件事。

完成栈和相关数据准备后，GSL 调用 `main_entry()`，继续执行用 C 编写的初始化
逻辑。能运行 C 函数，并不自动带来 Linux 服务：例如普通内存运算可以由指令完成，
读取文件、创建线程等能力还需要相应的系统实现。

## 4. 源码中的名字怎样变成地址

### 4.1 `.S`、目标文件、ELF 和启动镜像

`board_init_f`、`_start`、`__bss_start` 都是开发时使用的符号名。从源代码到
设备执行，中间经过以下处理：

```text
C 文件 → 编译、汇编 ──────────┐
                              ├→ 目标文件 → 链接 → ELF
.S 文件 → 预处理、汇编 ───────┘                       │
                                                       ↓
                                           按构建规则提取、压缩、打包
                                                       ↓
                                                 启动镜像
```

`.S` 文件通常先经过 C 预处理器，因此能使用 `#include`、`#define` 和 `#if`。
汇编器把指令转换为机器编码；如果目标地址还要等其他文件参与，目标文件会保留
符号引用和需要后续处理的信息。

链接器合并目标文件、分配布局并解析符号关系，形成 ELF。ELF 是一种组织代码、
数据及程序描述信息的文件格式，可以包含入口、装载描述、符号和调试信息。
设备最终读取的启动镜像还可能有专用镜像头、签名和压缩
内容；前一阶段按约定格式取得下一阶段需要的代码与参数。

### 4.2 标签、指令和链接脚本分别由谁处理

以下片段来自 GSL 的入口：

```asm
.globl _start
_start:
    b reset
```

`_start:` 为当前位置定义标签，`.globl` 让该符号能够参与跨文件的符号引用。
这两项由构建工具处理。`b reset` 则会形成跳转指令，设备运行时由 CPU 执行。

链接脚本 `.lds` 规定代码与数据的布局。GSL 的脚本包含：

```ld
ENTRY(_start)

/* MEMORY 中的区域定义 */
sram (rx) : ORIGIN = 0x4022600, LENGTH = 0x9400
```

`ORIGIN` 给出区域起点，`LENGTH` 给出链接布局可使用的长度。脚本后面的 `.text`
安排又把 `boot/start.o` 放在前面，因此入口代码能落在约定的位置。
`ENTRY(_start)` 将 `_start` 指定为输出程序的入口。
[GNU ld 的入口说明](https://sourceware.org/binutils/docs/ld/Entry-Point.html)
描述了链接器怎样处理这项设置。

U-Boot 的 `.S` 文件里还会出现 `ENTRY(_main)`。这里的 `ENTRY` 是头文件定义
的宏，用于展开符号声明、对齐和标签。虽然写法接近，它与 `.lds` 中的链接器命令
分别由各自的工具规则处理。阅读时先确认当前文件类型，再查符号或宏的定义。

构建工具完成这些工作后，运行阶段还要有人把内容放到约定位置，并让 CPU 进入
该位置。BootROM、GSL、U-Boot 和 Linux 的装载代码分别承担不同阶段的工作。

### 4.3 从一条反汇编看到符号和地址的对应

当前工作区的 GSL 反汇编中可以看到：

```text
04022600 <_start>:
 4022600: ea000016    b 4022660 <reset>
```

最左侧是指令地址，中间是机器编码，右侧是工具解码出的汇编和符号说明。
`_start` 对应 `0x04022600`，`reset` 对应 `0x04022660`。

这条 A32 分支采用相对偏移编码。它使用的 PC 基准为指令地址加 8，指令中的
偏移字段 `0x16` 左移两位，得到实际字节偏移：

```text
0x04022600 + 8 + (0x16 << 2) = 0x04022660
```

这就是这一次跳转怎样找到目标的具体依据。源码中的名字已经被构建工具落实为
地址关系和机器编码。读取 `pc` 和分析分支时需要确认指令集：A32 指令固定为
4 字节，Thumb 有 2 字节和 4 字节指令，不能把这条 A32 分支的计算套到所有指令。

## 5. 上电和异常怎样改变执行位置

### 5.1 第一次执行由复位机制建立

普通函数调用有前一条调用指令，上电后的第一次执行则由硬件复位机制建立。
电源、时钟和复位满足条件后，CPU 从规定的复位入口取指。芯片的地址映射决定
这次访问送到哪块存储器；在这条启动链中，CPU 因而读到 BootROM 中的指令。

地址映射可以理解为硬件对访问地址的分流规则：一段地址访问 ROM，另一段访问
SRAM，再一些地址访问外设控制接口。BootROM 开始执行以后，就可以通过这些
已经存在的硬件接口读取启动配置和后续内容。

BootROM、GSL 和 U-Boot 都是由 CPU 执行的程序。早期没有 Linux 进程环境，
它们通过准备内存、处理器状态和入口地址依次交接。

### 5.2 “寄存器”在源码中可能指三类对象

读初始化代码时，需要根据访问方式区分具体对象：

| 对象 | 示例 | 代码怎样访问 |
| --- | --- | --- |
| CPU 通用寄存器 | `r0`、`r1` | `mov`、`add` 等指令直接操作 |
| CPU 系统控制寄存器 | 异常向量基址、MMU 相关控制寄存器 | 使用对应的系统寄存器访问指令 |
| 外设寄存器 | UART、DDR 控制器的配置寄存器 | 按芯片规定的地址和访问宽度进行读写 |

向 RAM 写入数值会改变保存的数据；向设备映射地址写入数值，则可能改变硬件工作
状态。启动代码设置 DDR 时序或串口时，正是在按硬件要求配置这些接口。具体位的
含义、访问顺序和等待条件要与对应控制器的规定一致。

### 5.3 GSL 的 `smc #0` 为什么能到达 `boot`

GSL 的 `reset` 中有以下实际片段：

```asm
ldr r0, =reset_vect_table
write_mvbar r0
smc #0
```

`write_mvbar` 是这份源码定义的汇编宏，内部通过 `mcr` 指令写 MVBAR，也就是
Monitor 模式使用的异常向量基址寄存器。第一条先取得向量表地址，第二条把这个
地址告诉 CPU 的异常处理机制。

异常在这里指 CPU 转入特定入口处理事件的机制，例如响应一条主动触发异常的
指令。Monitor 是处理安全状态交接的一种 CPU 特权模式，处理代码仍由 CPU 执行。
通过配置入口和执行触发指令，软件可以使用处理器提供的这种状态切换能力。

异常向量表为不同异常安排规定的位置。`smc` 表示 Secure Monitor Call，会
触发相应异常；CPU 按该异常的规则进入向量表中的位置。当前 `reset_vect_table`
对应位置放的是 `b boot`，所以控制流接着进入 `boot`：

```text
软件把 reset_vect_table 的地址写入 MVBAR
                    ↓
执行 smc #0，触发 Monitor 异常
                    ↓
CPU 进入向量表中该异常对应的位置
                    ↓
执行该位置的 b boot
                    ↓
boot 准备栈和数据，再进入 C 代码
```

这里的 `#0` 是 SMC 指令中的立即数，目标入口来自异常处理规则和向量表配置。
读这种路径时，要把“触发异常”“进入向量位置”“执行向量中的跳转”连起来。
第 1 节的普通函数调用、这里的异常进入，以及上电复位，各有自己的入口来源。

## 6. 为什么同一个程序会涉及多个地址

### 6.1 先问每个地址用于哪个动作

一个程序存储、装载和执行的过程，会用到以下位置：

| 位置 | 它回答的问题 |
| --- | --- |
| Flash 偏移 | 从存储介质的什么位置读取内容 |
| 内存加载地址 | 读出的内容先写到哪里 |
| 链接时安排的运行地址 | 代码按什么位置布局，符号和地址引用按什么关系生成 |
| 实际执行入口 | 这次交接要从哪条指令开始 |

例如，加载器先把带镜像头的内容读到地址 A，再把其中的压缩代码解压到地址 B，
最后按镜像描述跳到入口 E。镜像头、压缩内容和可执行指令各自有用途，因而这些
地址有可能不同。要判断一个地址的含义，先看谁写入它、谁读取它，以及它用于
内存读写还是执行跳转。

### 6.2 链接脚本中的运行地址与装载地址

链接脚本还使用 VMA 和 LMA 描述一个段的运行地址与装载地址。GSL 中有这样的
实际布局：

```ld
.text.ddr : ALIGN(8) {
    *(.text.ddr);
} > ddr AT > sram
```

`> ddr` 把这一段的运行位置安排在 DDR 区域；`AT > sram` 把它的装载位置安排
在 SRAM 区域。`*(.text.ddr)` 收集各目标文件的同名段，`ALIGN(8)` 提出 8 字节
对齐要求。于是，GSL 可以先取得保存在 SRAM 中的内容，等 DDR 可用后再
把它复制到运行位置。链接脚本还提供边界符号，供复制代码取得源地址、目标地址
和长度。[GNU ld 对 VMA、LMA 和 `AT>` 的说明](https://sourceware.org/binutils/docs/ld/Output-Section-LMA.html)
给出了这种布局的具体规则。

这里的 VMA 是链接器的布局概念；是否经过 MMU 做地址转换，取决于执行时的处理器
配置。镜像在 Flash 中的偏移则还受最终打包布局影响，需要继续沿打包和读取代码
查找，才能与这些地址对应起来。

### 6.3 解压、复制和重定位分别改变什么

本平台的 U-Boot 启动内容先在 `0x41700000` 执行解压代码，将主体解压到
`0x41800000`，再进入主体。U-Boot 随后根据可用内存布局选择后续运行位置，
搬运自己并修正相关地址，这一步称为重定位。

解压把压缩内容还原成原始字节；复制将字节写入另一个位置；重定位还要处理程序
位置变化后的地址引用，并安排从新位置继续执行。U-Boot 会把自身和堆、栈等区域
安排好，为后续加载内核等内容留下明确的内存布局。

下面的目标地址和 `here` 位置是演算示例：

```text
原副本起点：      0x41800000
新副本起点：      0x43000000
位置差值：        0x01800000

原副本中的 here：0x41801200
新副本中的 here：0x43001200
```

如果某个需要调整的绝对地址还指向旧副本，复制后继续使用它就会访问原位置。
U-Boot 的 `relocate_code` 读取链接器生成的重定位记录，按记录类型修正相关
地址；当前 ARM 路径处理 `R_ARM_RELATIVE` 类型。程序布局和这些记录共同说明
哪些位置需要修正。

### 6.4 复制完成后，CPU 怎样到新位置继续执行

先约定这段代码的输入：U-Boot 用 `gd` 结构体保存启动信息，`r9` 指向它。
`gd->reloc_off` 保存位置差值，`gd->relocaddr` 保存搬运目标。相关汇编为：

```asm
adr lr, here
ldr r0, [r9, #GD_RELOC_OFF]
add lr, lr, r0
ldr r0, [r9, #GD_RELOCADDR]
b   relocate_code
here:
```

`adr lr, here` 取得原副本中 `here` 的地址。`GD_RELOC_OFF` 是字段相对 `gd`
开头的字节偏移，下一条因而读取 `gd->reloc_off`。`add lr, lr, r0` 再把差值
加到 `lr` 上，得到新副本中的 `here` 地址。

最后两条准备搬运目标，并跳到 `relocate_code`。这里使用 `b`，保留刚刚手动
算好的 `lr`；使用 `bl` 会重新写入返回位置。复制和地址修正完成后，该路径执行
`bx lr`，CPU 才开始在新副本中的 `here` 位置继续执行。

因此，复制数据和改变执行位置是两个明确的动作。CPU 后续到哪里执行，能够从
这些赋值和跳转指令中追踪出来。

## 7. 把这些机制放回 U-Boot 初始化

### 7.1 先建立早期工作区，再计算后续布局

U-Boot 主体经过 `_start`、`reset` 到达汇编入口 `_main`。当前普通启动路径
先选取栈地址、完成对齐，再调用 `board_init_f_alloc_reserve()`。这个函数通过
地址运算预留早期内存分配区和 `global_data`，把后者的地址作为返回值放进 `r0`。

接下来的片段是：

```asm
mov sp, r0
mov r9, r0
bl  board_init_f_init_reserve
mov r0, #0
bl  board_init_f
```

`sp` 被调整到预留区的下边界，栈从那里向低地址增长；`r9` 保存 `gd` 指针。
预留的数据完成初始化后，才进入 `board_init_f(0)`。

`board_init_f()` 通过函数指针数组 `init_sequence_f` 依次执行早期初始化。
本平台的 DDR 已由 GSL 准备好，这里继续确定可用范围并安排新位置，将结果写入
`gd`，包括：

| 字段 | 交给后续代码的信息 |
| --- | --- |
| `relocaddr` | U-Boot 的目标位置 |
| `reloc_off` | 需要调整的位置差值 |
| `start_addr_sp` | 下一阶段的栈位置 |
| `new_gd` | 下一阶段使用的数据副本位置 |

早期 C 环境有专门的约定：需要修改并保留的启动状态放在 `gd` 中，普通可写全局
数据和 `.bss` 在完整环境建立后再正常使用。`gd` 因而既是工作区，也是前后阶段
传递初始化结果的结构体。

### 7.2 两段 C 初始化之间由汇编完成交接

`board_init_f()` 返回到 `_main` 后，汇编从 `gd` 取得新栈和新数据地址，再执行
第 6 节的搬运和跳转。执行位置切换后，还要处理相关处理器状态、清零 U-Boot
自己的 `.bss`，最后进入 `board_init_r()`。

```text
board_init_f()
    计算后续布局，将结果保存在 gd
          ↓ 返回汇编
切换栈和 gd，重定位代码，建立完整运行环境
          ↓ 进入后续 C 代码
board_init_r()
    初始化内存分配器、存储、环境变量和控制台等
          ↓
main_loop()
    处理自动启动命令或命令行输入
```

进入 `board_init_r()` 前，`mov r0, r9` 传递 `gd`，
`ldr r1, [r9, #GD_RELOCADDR]` 传递目标地址，对应
`board_init_r(gd, gd->relocaddr)` 的参数关系。

当前配置启用 `CONFIG_SYS_THUMB_BUILD`，入口交接使用：

```asm
ldr lr, =board_init_r
bx  lr
```

这一次 `lr` 保存的是函数入口，`bx` 因而进入该函数。`bx` 还会依据目标最低位
携带的信息选择 ARM 或 Thumb 指令状态。分析真实跳转时，要结合编译配置和指令
编码；固定地址示例只帮助理解位置关系。

后续 `board_init_r()` 通过 `init_sequence_r` 完成初始化，最终进入
`main_loop()`。U-Boot 读取环境中的启动设置，执行相应命令。`nand read` 把
镜像读进内存，`bootm` 解析镜像并准备交接，随后才进入内核入口。

## 8. 从跳入内核到运行应用的 `main()`

### 8.1 交接入口的同时，还要交接参数和处理器状态

U-Boot 的 ARM Linux 交接代码将入口保存为函数指针，再按准备好的参数调用：

```c
kernel_entry(0, machid, r2);
```

在当前 32 位 Arm Linux 启动协议中，入口处 `r0` 为零，`r1` 携带机器类型
信息，`r2` 指向设备树或传统启动参数。设备树是描述硬件组成与连接的数据；内核
拿到地址后，才能读取其中的内容。`bootargs` 则表达本次控制台、根文件系统等
启动选择。

协议还规定进入内核时 MMU、缓存和中断等状态。这些准备让内核入口能按共同的
条件开始运行。入口处怎样使用寄存器，要结合这份协议与入口代码理解。
[Linux 5.10 ARM 启动协议](https://docs.kernel.org/5.10/arm/booting.html)
列出了这些交接要求。

### 8.2 MMU 为什么出现在内核早期汇编里

MMU 是 CPU 中负责地址转换和访问保护的硬件。启用地址转换后，程序使用虚拟地址，
MMU 根据页表将它转换为物理地址，再由芯片地址映射访问对应内存或设备。页表是
内存中的映射数据，由系统软件准备。

```text
程序使用的虚拟地址
        ↓ MMU 根据页表转换
物理地址
        ↓ 芯片地址映射
RAM 或设备
```

内核必须先准备切换时需要的映射，再开启相应功能，否则下一条指令或栈访问可能
就找不到正确位置。当前 ARM 内核从 `head.S` 中的 `stext` 开始，建立早期页表，
安排 MMU 切换，随后在 `__mmap_switched` 路径准备相关数据和栈、清零 `.bss`，
再进入 C 函数 `start_kernel()`。

改变映射可以让同一块物理内存通过另一个虚拟地址访问；复制程序则会在另一块内存
写入字节。阅读“地址发生变化”时，需要分清代码做了地址转换、内容搬运，还是
同时处理了两者。

### 8.3 内核开始执行以后，应用还缺什么

`start_kernel()` 继续建立内存管理、调度、中断和设备等设施。后续内核初始化
需要找到用户态初始化程序，才能组织应用启动。这引出了根文件系统的作用：
内核镜像提供内核代码，而 `/sbin/init`、Shell、动态库和启动脚本通常由文件系统
提供。

本平台普通启动从 NAND 上的根卷取得这些文件：MTD 提供原始 Flash 访问抽象，
UBI 管理其上的卷，UBIFS 在卷上组织目录和文件。把根文件系统挂载到 `/` 后，
内核才能沿路径找到用户态程序。存储驱动和文件系统支持必须在访问它们之前可用。

内核创建 PID 1 后，由相应路径继续初始化并执行用户态 init。当前使用 BusyBox
初始化配置，init 据此运行启动脚本；脚本再挂载产品卷、设置环境并启动应用。
因此，能看到内核日志、根文件系统挂载成功、init 运行和应用运行，是不同的启动
进展，需要分别观察。

### 8.4 应用的 `_start` 怎样到达 `main()`

应用启动已经有 Linux 负责装载。执行程序时，内核读取 ELF 中的程序头，按可装载
段建立进程的程序映像，并准备用户栈和入口状态。若 ELF 指定了动态解释器，内核
会先安排动态加载器执行，由它完成相应动态装载和链接工作。

```text
启动脚本请求执行应用
        ↓
内核按 ELF 描述建立程序映像和初始执行状态
        ↓
动态加载器完成装载准备（动态链接程序）
        ↓
应用启动入口及 C 运行时初始化
        ↓
main()
```

应用启动入口通常也名为 `_start`，由工具链和运行库提供。`_start` 是各自程序
中的符号名，所以 GSL 的 `_start`、U-Boot 的 `_start` 和应用的 `_start`
分别对应不同程序中的位置。

ELF 中的 section 常用于链接组织，运行装载主要依据 program header 描述的
segment。`readelf -h` 可以看入口等 ELF 头信息，`readelf -l` 可以看可装载段和
解释器，`readelf -S` 可以看 section；这些命令在宿主机解析文件内容。
[ELF Program Loading](https://gabi.xinuos.com/elf/07-pheader.html)
说明了程序头怎样描述运行中的程序映像。

走到 `main()` 时，应用需要的系统环境已经建立。CPU 此后仍在执行指令，但应用
通过 Linux 管理的地址空间、调度和系统调用使用资源。沿启动代码向前追踪，看到的
就是这些条件从硬件复位开始逐步建立的过程。
